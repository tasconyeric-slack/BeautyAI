执行摘要

如果只读一页，读这一页。下面九个判断是整份方案的骨架，后文逐一展开；怎么开工见 G。

我们要做的是一位线上形象顾问：先让用户被准确地“看懂”，再让她在自己身上看见几种可能，最后带着一份能直接用的清单去改变。线下顾问一次收费数百到上千元，我们用一张自拍和几分钟交付其中最有价值的七成，并且如实说明剩下三成的不确定。

复用现有引擎，并行开发，尽早上线

V1 的质检、锚点、取色、结构化分析、规则层与蒙版回贴都已可用。V2 不推倒重来：在现有 schema 与 API 上扩展，契约先行，再按四条工作流并行开发。关键路径只用 5–10 组经同意的照片验证一次；40 人评测集、专家盲评与评测看板改为上线后的持续工作，不阻塞交付。隐私、身份保护、AI 标识与数据删除这些保障不放松。

核心产出是“形象档案”，它同时是分享物

档案由三项构成：面部美学（脸型、三庭五眼、轮廓与五官量感）、个人色彩（冷暖、深浅、清浊、对比）、风格类型（量感 × 曲直 → 八种风格）。这三项正是小红书上被讨论最多的形象话题，做成一张 3:4 档案卡，就是用户愿意发的“我测了我的风格类型”。

档案之后是四类推荐，每类都能在本人身上看见

发型（三个方向试看）、妆容（确定性试色：唇色、腮红、色调，带牙齿与眼睛排除蒙版，可随时对照原图，不做五官重塑）、色彩（数字披布：在下巴下方换颜色对比）、穿搭（按风格、色彩、自选身形给出单品与搭配公式）。可视化是让用户相信的核心。

先做“美学分析”，颜值评分作为未来功能预留

面部美学的主体是解释比例、轮廓与量感，以及它们对发型、妆容、穿搭意味着什么。颜值评分保留为潜在的未来功能：本期不建评分模型，不把几何公式包装成已验证的分数，只放一个标注“即将上线”的预告入口测量兴趣。开发用的 10/10 占位分只存在于开发样例里，永远不对外展示。真实评分上线前需要单独验证并新增决定记录。评分工作不得拖慢其他任务。

上传一张正脸起步，30 秒内给出第一个发现

本地上传是主入口，只要求正脸；保留上传质检、拍摄指南与重拍建议，本期不做实时相机取景（列为后续增强）。侧脸选填；问卷改为看图选择，并放在第一个结果之后。CV 测量 1 秒内就能出结果，把它变成“揭晓”时刻。全身照只在用穿搭检测时才需要。

穿搭分两层：先“推荐”，再“检测”

穿搭推荐是一次性的方案（风格 + 色彩 + 身形 → 单品清单）；穿搭检测是高频工具（拍今天的穿搭 → 颜色、风格一致度、比例线的建议）。前者带来信任，后者带来复访理由（本期包含在付费完整护照内，不做会员）。身形只来自用户自选或填写，不从照片推断体型或体重；穿搭检测只分析衣物颜色、廓形与画面构成。

反馈从第一个版本就在

“像我 / 不像我”“我更喜欢另一种风格”、对发型与穿搭的喜欢 / 一般 / 不喜欢、可选原因，以及更新预算、打理时间、场合，都由规则层即时重排或过滤，不重跑视觉模型。系统观察到的特征与用户的偏好分开存储，互不覆盖。

把 V1 的“来源标签”降到第三层

测量 / 模型 / 规则 标签对评审者是亮点，对消费者是噪音。V2 改为每个结论旁一个“依据”入口，点开后在用户自己的照片上高亮对应区域。

北极星：带走率；增长引擎：档案卡与揭晓视频

带走率指完成档案的用户中，保存或分享至少一张决策卡（发型师卡、色卡、穿搭清单）的比例。增长靠两类产出：3:4 档案卡（小红书笔记）和自动生成的 9:16 揭晓视频（抖音），卡片默认用插画头像或色卡艺术，本人肖像可选；全部带 AI 标识与产品署名。

怎么交付：Claude Code 先定共享契约（schema v0.3、API、前端外壳），独立智能体同时开发知识库、组件与分享卡模板。四条工作流：A 核心档案与分享、B 造型与试看、C 高级互动与持久化、D 分发与单次付费。增量 1 免费档案（上传 → 档案 + 披布 + 基础反馈 + 档案卡 + 1 张发型试看 + 话题入口）→ 增量 2 造型试看 + 付费完整护照 → 增量 3 穿搭检测、详细分析、轻账户 → 增量 4 揭晓视频与真实支付。详见 F 与 G。

A4The Face Report 深度拆解

它做对了什么

  • 获客机器：23 个免费单点工具（脸型、对称度、眼型、瞳距、色彩、发型查找……）加约 40 篇指南文章，组成 SEO 矩阵；首页宣称“30 天 25 万次扫描”。
  • 零摩擦开始：一张正脸、免注册；免费扫描在浏览器本地运行，“照片不离开设备”。
  • 清晰的升级路径：先免费测，再一次性付费 $17.49 买完整报告（含 6 张发型试看、12 季型色彩、四周计划、PDF），7 天无理由退款，另售 $9.99 起的 AI 积分包。
  • 发型卡片结构好：每张试看带“推荐 / 稳妥替代 / 大胆选择”标签、打理时间、修剪周期、分线、层次、取舍说明，以及“喜欢 / 也许 / 不要”按钮。
  • 行动计划字段完整：类型、频率、首次见效时间、投入、成本区间、置信度、“为什么先做这个”。

它的弱点（我们的机会）

  • 以分数为核心：0–100 分、百分位、“领先 X% 的扫描”。报告自称“分数不是目标”，却又把 1.23 的比例称为“完美 100/100”。这种矛盾会伤害信任，也有明显的心理风险。
  • 测量多、决策少：40+ 项测量里，大部分（眼角倾斜、鼻部投影）无法转化为用户能做的事。
  • 泛化建议：烟酰胺、BHA、维 C 这类护肤建议与测量结果无关；还有“仰睡避免不对称”这类无依据说法。
  • 重复与填充：不同发型卡共用同一段取舍说明；名人脸对比没有方法；“四周计划”付费后只见到三条和一个锁定卡。
  • 擦边医美：附加的“Procedure Preview”、指南中的 mewing、下颌角等内容，把用户推向外貌焦虑。
  • 英文、西方审美与发型库：中文用户、亚洲发质与国内理发店的沟通方式没有被服务。

B4风格诊断体系：八型标签 + 四层区分

小红书上流行的“风格诊断”就是量感 × 曲直平面上的八种类型。V1 已经输出量感（visual_weight 1–5）和曲直（angular_rounded −2…+2）两个连续维度，规则层按最近原型推导标签，临界时显示“介于 A 与 B 之间”（D2）。这一体系可以直接产品化。

V2 的改进：① 用平面图展示用户的位置和离其他类型的距离，而不是只给一个标签；② 区分“面部风格”（只看脸）和“整体风格”（加上用户自选的身形骨架和身高后）；③ 每种风格附带具体的面料、廓形、图案、配饰规则，直接连到穿搭推荐；④ 男性表达方向使用对应的词表（例如“少年型”“自然型”“戏剧型”），由用户自选的表达方向决定（D9）。

四层区分（定稿）：八个标签保持小红书通行叫法：少女型、少年型、优雅型、浪漫型、自然型、古典型、戏剧型、前卫型。产品中把风格信息分成四层，分别存储、分别展示：
① 可观察的面部特征（CV 测量与模型观察，例如“轮廓线条偏直”）；② 推断的风格类型（规则层按最近原型推导的位置与标签）；③ 个人审美偏好（用户选的喜欢 / 不喜欢的风格）；④ 想要的目标形象（用户选的“想成为的样子”）。推荐以②为底、③④为方向；用户说“不像我”只改变偏好层与展示，不改写①和②。示例图与词表按表达方向（女性化 / 男性化 / 中性）调整，八型本身不变。

风格八型是行业惯例而非科学分类，界面上称为“风格方向”，不称“诊断结果”，并说明它描述的是视觉印象。

真人案例（I1 关键路径验证时征得 3–5 位授权，不足时用插画）；现有 /sample 报告组件；设计系统组件（G 节 K4）。

上传一张正脸：快速扫描与重拍建议

›把开始门槛从“2 张必填 + 3 步问卷”降到“上传 1 张正脸”，并让第一张照片尽量合格。 A · 1
用户问题

45° 侧脸独自难拍；相册照片多带美颜、逆光或角度偏；用户在不知道回报之前不愿投入。

预期结果

用户 45 秒内上传一张合格正脸，并在 20 秒内看到第一个关于自己的发现。

体验与交互
  1. 同意页（首次）：三行说明照片用途、保留时长与删除方式；单独勾选“同意处理我的人脸照片”和“已满 14 周岁”。
  2. 上传页：一个大的上传区（手机上点开即是系统的“照片图库 / 拍照”选择），旁边是一张“好照片”示例与四条要点：正对镜头、自然光、露出额头和发际线、关掉美颜。
  3. 选完照片后 300 ms 内给出质检结果：合格直接进入揭晓；不合格时只显示一条最重要的原因和具体做法（“光线从背后来，换个方向再拍”“脸太小，请裁近一点或靠近一些”），并附“仍然使用这张”（结论降级）与“换一张”。
  4. 疑似美颜（脸颊纹理过度平滑）：提示“这张可能开了美颜，结果会偏差。可以继续，也可以关掉美颜重拍”。
  5. 之后直接进入 F4 的揭晓，不先填问卷。只问一个问题：“你想看哪种表达方向的建议？”（女性化 / 男性化 / 中性，三张示意图），可跳过，跳过时给中性建议。
功能需求
  • 只用 <input type="file" accept="image/*">；不调用 getUserMedia，不加载 MediaPipe WASM。前端只做压缩与 EXIF 方向校正（沿用 web/components/analyze/photo-slot.tsx）。
  • 服务端质检沿用 POST /api/qc 与 config/qc.yaml，新增 beauty_filter_suspect（脸颊区域 Laplacian 方差下限）与面向用户的中文重拍文案表。
  • 只需要 front：pipeline 的 REQUIRED_ROLES 改为 ("front",)；profile45、smile、hair 为可选（D14 修订）。
  • 非正脸照片在任务结束后删除；正脸、缩略图与试看图保留 24 小时（沿用不变量 7）。
状态与边界
  • 多张人脸：提示“只保留你自己”，请用户裁剪后重传。
  • 戴眼镜：允许；提示“摘掉能让眼镜建议更准”。
  • HEIC 等格式：前端转换失败时由服务端转换；仍失败则提示换一张。
  • 超大图片：前端压缩到长边 2048 px 再上传。
依赖

qc.py、cv.py、现有上传向导（wizard.tsx、photo-slot.tsx）；美颜检测为新增启发式。

验收标准
  • 只传正脸即可生成护照（假模型下端到端测试）。
  • 每一种质检拒绝原因都有对应的中文重拍建议（测试覆盖全部原因码）。
  • 合成美颜图（双边滤波强度 ≥ 中）检出率 ≥ 80%，正常照片误报 ≤ 10%（合成样本测试）。
成功指标
  • 开始 → 获得第一个发现 ≥ 70%。
  • 重传次数中位数 ≤ 1。

后续增强（不在本期）：实时相机取景（椭圆引导框、实时提示、自动拍摄），需要 getUserMedia 与前端 MediaPipe WASM，待上传版的转化数据证明值得再做。

渐进式补充：侧脸、发质、身形与“想要的感觉”

›在用户看到价值之后，再用图片而不是抽象词收集让结果更准的信息。 A · 1
用户问题

“松弛”“有分量”这类词用户无法对应到具体样子；又缺少发质、留长意愿等对发型推荐至关重要的信息。

预期结果

补充信息的完成率高，且每项都能在结果中看到它的作用（“因为你说不想每天吹头，省心方向用了免吹剪法”）。

体验与交互
  1. 快速洞察页底部出现“解锁完整护照”卡，列出补充项和各自带来的变化，每项都可单独完成。

  7. 穿搭现状：从风格图卡中选出“平时最常穿的三套”，用于判断现状与目标的距离。
  8. 现实条件：每天打理时间（0 / 5 / 10 / 20 分钟）、理发预算（每次）、能接受烫 / 染、愿不愿意留长 2 个月、主要场合。全部有默认值。
功能需求
  • user_context（schema v0.3）新增：hair{texture, density, grow_out_ok}、haircut_budget、occasions[]、body{frame, height_cm}（仅用户输入）、style_preferences{liked[], disliked[]}、target_style、current_style_picks[]。
  • A/B 图片对使用插画或授权案例，且覆盖三种表达方向。
  • 只有新照片或影响模型输入的字段变化时才触发完整分析（F4）；偏好、预算、场合、身形的变化只触发规则层重排。已有结果不消失。
状态与边界
  • 用户跳过全部补充：完整护照仍可生成，置信度和“依据不足”提示随之变化。
  • 侧脸质检失败：不阻塞，提示可稍后补。
依赖

passport.schema user_context 扩展（schema v0.3）；analyzer prompt 需描述新字段。

验收标准
  • 每个补充项在报告中至少有一处可见引用。
  • 完成全部补充的中位时长 ≤ 90 秒。
成功指标
  • 快速洞察 → 完整护照 ≥ 45%。
  • 侧脸提供率 ≥ 50%（V1 为强制，需对比质量差异）。

分析进度：等待时就开始给发现

›把等待变成揭晓过程：CV 结果即时出现，模型结果分段到达。 A · 1
用户问题

V1 在完整分析结束前只显示阶段列表；而 CV 测量 1 秒内就绪。完整分析可能超过 1 分钟，用户易流失。

预期结果

用户在 3 秒内看到第一个与自己相关的内容，在 20 秒内看到结构签名，整段等待都有新信息出现。

体验与交互
  1. 第 0–3 秒：用户照片出现在深色舞台上，关键点轮廓线淡入（只画轮廓与比例线，不画 478 个点）。
  2. 第 3–8 秒：测量结果逐条“盖章”出现，例如“面部长宽比 1.42 · 偏修长”“上中下庭 0.31 / 0.34 / 0.35”。
  3. 第 8–20 秒：快速模型返回 3 条结构签名与一句话总结，替换为可阅读的“初见”卡。
  4. 完整分析在后台继续：顶部细进度条与当前阶段文字；期间用户可以继续补充 F3 信息。
  5. 完成后推送页内提示“你的形象档案已准备好”，试看图逐张出现。
功能需求
  • 沿用现有轮询 GET /api/passport/{id}，响应新增 partial 快照：anchors、quick、analysis、previews 各自就绪即返回。轮询间隔 1 s 起、逐步放宽到 3 s。SSE 列为后续优化，不在本期范围。
  • 快速分析为一次独立的轻量模型调用（输出 ≤ 1k token，仅含 observations 子集与 feature_signature），属于独立请求，仍满足“每次请求一个生产模型”。
  • 刷新页面后从轮询快照恢复。
状态与边界
  • 快速分析失败：仍显示 CV 测量与“完整分析进行中”。
  • 完整分析校验两次失败：保留快速结果，提示“完整护照生成失败，可免费重试一次”。
  • 超时 > 3 分钟：可留下邮箱或保存链接，完成后再看。
依赖

pipeline.py 拆成两段；api/jobs.py 写入分段快照；前端沿用现有轮询（web/lib/api.ts）。

验收标准
  • 首个个性化内容出现 p50 ≤ 3 s。
  • 等待期内没有超过 10 秒无新内容出现的空白段。
成功指标
  • 等待期流失率 ≤ 10%。
  • “初见”页的 CSAT（一题：“这说的像你吗？”）≥ 4.0/5。

形象档案（第一层）：脸 · 色彩 · 风格

›一屏讲清你是什么样、先做哪件事、去哪里看可能性；同时是分享卡的原型。 A · 1
用户问题

V1 的头卡不错，但 10 个区块平铺；用户不知道看完之后最该做什么，也没有一个值得分享的“结果”。

预期结果

用户在一屏内得到三张档案（面部美学、个人色彩、风格方向）、一件“先做这个”，以及四类推荐的入口；超过一成的用户分享档案卡。

体验与交互
  1. 封面：本人照片在深色舞台上 + 一句话总结（例如“柔和的中等量感，适合低对比、带一点曲线的造型”）。
  2. 三张档案卡横向排列：面部（脸型 + 3 条结构签名）、色彩（色彩方向 + 6 个近脸色）、风格（平面图上的位置 + 风格方向名）。每张可点进对应的第二层页面。
  3. 先做这一件：排序第一的建议，附投入（时间 / 费用）与“看看效果”。
  4. 为你推荐：发型、妆容、穿搭、配饰四个入口，各带一张缩略试看。
  5. 像我吗？每张档案卡下方“像我 / 不太像”；选“不太像”可选原因（例如“我觉得更偏优雅”），进入 F16 基础反馈。
  6. 顶部“分享档案卡”：生成 3:4 卡片，视觉可选插画头像、色卡艺术或本人肖像（F17）。
  7. 付费内容（完整推荐）以“解锁完整护照”卡出现在推荐入口处；免费内容本身完整可用，不打码（见 F4）。

  • 新增 analysis.feature_signature[3]：title（≤12 字）、observation_ids、region、styling_implication。
  • 照片高亮多边形由规则层从 CV 关键点生成，模型不给坐标。
  • 照片 24 小时后删除：封面切换为插画头像 + 档案文字，注明“照片已按承诺删除”。
状态与边界
  • 只有快速结果时：色彩与风格卡显示“完整分析中”骨架，面部卡先出。
  • overall_confidence < 0.4：顶部提示“照片条件有限，以下结论偏保守”，并给出最有效的一条补拍建议。
依赖

header.tsx、evidence.tsx 改造；schema v0.3；rules 区域映射。

验收标准
  • 375 px 宽度下，封面、三张档案卡和“先做这一件”在两屏以内。
  • 5 位测试者中至少 4 位能复述自己的风格方向和一个适合的颜色。
成功指标
  • 档案 → 进入任一推荐 ≥ 75%；档案卡分享率 ≥ 10%。

面部美学分析

›解释脸型、比例、轮廓与五官量感，以及它们对发型、妆容、配饰的意义。本期只做分析，颜值评分为预留的未来功能。 A · 1
用户问题

用户想知道“我的脸是什么样的、为什么有些发型和妆容不适合我”。竞品要么给一堆测量和分数（The Face Report、颜大师），要么只给一个脸型标签。

预期结果

用户看懂 4–6 条关于自己面部的关键特点，每条都在照片上有依据，并知道它影响哪些选择。

体验与交互
  1. 比例图：三庭（上 / 中 / 下庭占比）与五眼（眼宽与眼距关系）画在用户照片上，数字用等宽体；旁边只写一句解读，例如“中庭略长，适合用刘海或横向眉形把视线拉回中部”。
  2. 轮廓：脸型候选与概率（临界时显示“介于 A 与 B 之间”），额、颧、下颌三处宽度对比条。
  3. 五官量感：五官整体偏大或偏小、线条偏柔或偏利，与风格诊断联动。
  4. 你的特点：3 条结构签名，用中性词描述，例如“下颌线清晰”“眉眼间距较近”“唇形饱满”。
  5. 所以：每条特点下列出它影响的推荐（发型 / 妆容 / 眼镜 / 领口），点击直接跳转。
  6. 颜值评分 · 即将上线（开关控制）：页面底部一张预告卡，写“我们在验证一种讲依据的评分方式”，按钮“上线时告诉我”。只记录兴趣事件，不显示任何分数、示例分或几何“得分”。
功能需求
  • 三庭五眼由 CV 测量（anchors.py 已有中下庭比、眼距比；补充上庭与眼宽），写入 anchors，模型只做解读。
  • 不显示“标准值”或“理想比例”；如需参照，只显示“常见范围”的灰色带，并注明“范围不代表好坏”。
  • 扩展 safety_terms：模型输出中继续拦截“完美”“标准脸”“缺陷”“颜值”“打分”“评分”等词。预告卡是前端固定文案，不经过模型，因此不冲突。
  • 开发用的 10/10 占位分只允许出现在 web/lib/fixtures 的开发样例中；生产构建不得渲染任何分数（自动化测试校验）。不得把三庭、对称度等几何公式包装成分数。
状态与边界
  • 刘海遮住额头：上庭标注“被刘海遮挡，未测量”。
  • 头部偏转超过阈值：五眼不显示，只给轮廓结论。
  • 无侧脸：不出现下颌角、侧面轮廓相关结论。
依赖

anchors.py、face_shape.py、observations；how-we-know.tsx 中的维度条可复用。

验收标准
  • 安全词检查 0 命中；生产构建中不出现任何分数（测试）。
  • I1 小样本中同一人两张照片三庭比例差 ≤ 0.02。
  • （上线后跟踪）形象顾问认为解读合理且有用 ≥ 75%。
成功指标
  • 美学页 → 点击“所以”跳转推荐 ≥ 40%；“这说的像你吗”≥ 4.0/5。

个人色彩与数字披布

›告诉用户哪些颜色放在脸旁边、哪些做衣橱底色、买东西时怎么用。 A · 1
用户问题

V1 的四轴刻度与色族名对普通用户太抽象；冷暖置信度常被封顶在 0.45，结论模糊却没给出改善方法。

预期结果

用户拿到三组色卡并理解“近脸 / 衣橱 / 慎用”的用法；需要时可做 20 秒的白纸校准提升置信度。

体验与交互
  1. 近脸色（上衣、围巾、镜框）6–8 色；衣橱底色（外套、裤装）4–6 色；慎用色 3–4 色。每色有中文名。

  • 测量可靠性低：只显示近脸色中最稳妥的中性色，并提示校准。

风格诊断：八型 · 四层

›把量感与曲直维度产品化为八种“风格方向”，并把“我看起来像什么”和“我喜欢、我想成为什么”分开。 A · 1
用户问题

“我是什么风格”是小红书上最受欢迎的形象话题之一，但现有工具多为问卷测试，结果像星座；而且把“适合”与“喜欢”混在一起，用户不认同时无处表达。

预期结果

用户看到自己在量感 × 曲直平面上的位置、主风格与相邻风格；能说出“我更喜欢另一种”，推荐随之调整，但系统对她面部特征的观察不被覆盖。

四层（定稿）
  1. 可观察的面部特征：CV 测量与模型观察（例如“轮廓线条偏直”“五官量感中等”），带观察编号，可在照片上高亮。
  2. 推断的风格类型：规则层按最近原型推导的位置与八型标签（少女、少年、优雅、浪漫、自然、古典、戏剧、前卫），临界时显示“介于 A 与 B 之间”。
  3. 个人审美偏好：用户选的喜欢 / 不喜欢的风格（F3、F16）。
  4. 想要的目标形象：用户选的“想成为的样子”。

推荐以第 2 层为底，向第 3、4 层倾斜；页面上四层分开显示，用语不同（“你的特征”“看起来像”“你喜欢”“你想去”）。

体验与交互
  1. 平面图：八种风格分布，用户位置是一个点和一个不确定性圆圈；若用户有偏好或目标，用空心点标出，并画一条“过渡箭头”。
  2. 为什么在这里：两条依据，例如“五官量感中等偏大（o3、o7）”“轮廓线条偏直（o2）”。
  3. 你的风格规则：面料、廓形、图案大小、配饰尺寸、领口形状，各一行。
  4. “像我 / 不太像”与“我更喜欢另一种风格”：选择后立刻重排穿搭与发型推荐，并显示一行“已按你喜欢的优雅方向调整”。
  5. 过渡方案：从“看起来像”走向“想去的”，保留什么、加入什么。
  6. 示例图、词表与规则按用户自选的表达方向切换（女性化 / 男性化 / 中性）；八型本身不变。
功能需求
  • 复用 style_dimensions 与 rules.style_label 的最近原型；原型坐标仍在 config/rules.yaml，八型规则表与按表达方向的示例放 config/styles.yaml（智能体 K1 编写）。

  • 新增 derived.style_profile：face_only、overall（加入自选身形后）坐标、primary / secondary、between、preference_overlay{liked, disliked, target}、rules_zh。
  • 偏好与目标存于 user_context 与 preference_events，不写入 analysis。
状态与边界
  • 维度置信度低：只显示大区域（例如“直线感、中等量感”），不给具体类型。
  • 用户偏好与推断相距很远：不争辩，只说明“看起来像”的依据，并给过渡方案。
依赖

rules.py 风格推导（D2）；styles.yaml（K1）；StylePlane 组件（K4）；F3 偏好与身形。

验收标准
  • 八个标签在三种表达方向下都能渲染，并有各自的示例与规则。
  • “我更喜欢另一种”只改变 preference_overlay 与排序，analysis 与 face_only 坐标不变（测试）。

发型顾问：三方向试看、比较与发型师卡

›回答“什么适合我、看起来什么样、怎么剪出来”。V2 的核心功能。 B · 2（1 张试看在增量 1）
用户问题

V1 只预览第一条建议，用户无法比较；文字参数（“顶部 5–6cm”）难以想象；话术藏在长卡片里；用户无法表达“我不喜欢这个”。

预期结果

用户在 2 分钟内比较 3 个有明显差异的方向，选定 1 个并保存发型师卡；不满意时 1 次反馈后能得到更贴近的新方向。

三个方向的定义
  • 稳妥：在现有长度内调整，剪一次就能实现，风险最低。
  • 突破：变化最明显，可能需要留长、烫或改分线；说明需要多久。
  • 省心：每天打理 ≤ 3 分钟、修剪周期最长。

三者必须在长度、轮廓或刘海中至少两项上不同（规则层校验），避免三张“差不多”的图。

体验与交互
  1. 顶部：深色舞台上的大图，默认显示“稳妥”；下方三个缩略图切换方向，加一个“现在”。
  2. 大图支持按住看原图、左右拖动对比；提供“正面 / 45°”切换（有侧脸时）。
  3. 大图下：方向名（中文常用叫法 + 英文术语）、一句“为什么适合你”（引用签名）、参数条（长度、顶部高度、两侧、刘海、分线、纹理），打理成本（每天几分钟、几周修剪一次、每次约多少钱）。
  4. 反馈按钮：“喜欢”“一般”“不喜欢”。选“不要”时出现原因标签：太短 / 太长 / 太普通 / 太夸张 / 打理太麻烦 / 不适合我的工作。
  5. “再给我一个方向”：根据反馈生成第 4 个方向（每份护照最多再生成 3 次；增量 3）。
  6. 免费版：只生成“稳妥”方向 1 张试看；付费完整护照：三方向、比较、发型师卡与再生成。
  7. “比较”模式：任选两张并排，参数差异高亮。
  8. “就选它”：生成发型师卡（F9.1）。
功能需求
  • 模型输出 hair_options[3]（取代 named_styles），每项含 tier、参数、打理、需不需要烫染、发型师话术、visual_edit_spec、evidence、confidence。
  • 规则层：约束过滤（不接受烫染则突破方向不得依赖烫染）、差异度校验、款式库匹配（mm 参数）。
  • 三张试看并行生成；每张独立失败、独立重试。
  • 反馈写入 preference_events；“再给我一个”是一次新的模型请求，输入包括已看过的方向与反馈原因。
  • 每张试看图左下角显示“AI 试看”标识，并写入隐式元数据。
  • 女性常用参数：长度（下巴 / 锁骨 / 肩下 / 胸前）、刘海（空气 / 八字 / 齐 / 无）、卷度（直 / C 卷 / 法式波浪 / 羊毛卷）、发色方向；男性沿用 V1 参数（两侧、顶部、刘海、分线）。
F9.1 发型师卡
  • 一张竖版卡片：试看图（可选择隐藏脸部，只留发型区域）、款式名、三段话术（“两侧……”“顶部……”“刘海……”）、mm 参数表、“请不要”清单、参考款式编号。
  • 操作：保存图片、复制文字、生成只读链接（链接不含照片，除非用户勾选）。
  • 话术用发型店口语，例如“长度剪到锁骨下一指，前面做八字刘海，最短到颧骨，发尾不要打太薄”。
状态与边界
  • 某张试看失败：显示参数插画 + “重试”，不影响其他两张。
  • 身份检查未通过（E4）：不展示该图，自动重生一次，仍失败则降级为插画。
  • 长发、刘海遮挡面颊的方向：使用“软保护”回贴（见 E4），否则会被截断。
  • 用户当前是光头或极短发：突破方向标注“需要留长约 X 个月”。
依赖

preview.py、masks.py、providers/image；config/hairstyles.json 扩充到 60+ 款并加入中文名与亚洲发质适配（K3）；schema v0.3 的 previews[]。

验收标准
  • 三方向在长度、轮廓、刘海中至少两项不同（规则层测试）。
  • 假模型下三张试看并行生成、各自失败各自重试；五官核心区逐像素不变（测试）。
  • I1 小样本中长发与刘海方向无截断。
  • （上线后跟踪）“像本人”≥ 90%；发型师认为可直接照着剪 ≥ 80%。
成功指标
  • 护照中保存发型师卡比例（带走率）≥ 40%。
  • “不要”之后再生成的方向被标为“喜欢”的比例 ≥ 50%。

穿搭推荐

›把风格、色彩与身形转化成单品清单、搭配公式和场合方案，并能落到购物搜索。 B · 2
用户问题

知道了“我是自然型、柔和夏”，用户仍不知道明天该买什么、怎么搭。现有穿搭 App 多为模板推荐或商品流，和“我”的特点没有联系。

预期结果

用户得到 8–12 件核心单品、3–5 个搭配公式和 3 个场合方案，每件都说明“为什么适合你”，并能一键复制搜索词去淘宝、小红书。

体验与交互
  1. 你的穿搭公式：3–5 条，例如“低饱和蓝灰上衣 + 米色直筒裤 + 细金属配饰”，每条配插画平铺图与色块。

  3. 场合方案：通勤、约会、正式场合三个标签，各一套完整搭配。
  4. 购物：每件单品给出 2–3 个搜索词（“雾蓝色 真丝衬衫 宽松”），复制即可；以后若接入电商链接，明确标注合作。
  5. 领口试看：对近脸的上衣颜色与领口，可在本人照片上做披布或领口换色对比（F7 能力复用）。
  6. 每件单品与公式可“喜欢 / 一般 / 不喜欢”（F16 基础反馈，即时重排）；单品另可标“已有”，进入简单衣橱，为穿搭检测（F12）提供上下文。
功能需求
  • 单品本体库 config/garments.yaml（智能体 K2）：品类、廓形、面料、领口、适合风格、适合身形骨架、表达方向，约 150 条起步。
  • 模型输出 outfit_direction：formulas[]、items[]（引用单品库 id）、occasions[]、evidence；规则层校验单品与风格、色彩、约束的一致性（例如“慎用色”不得出现在近脸单品中）。
  • 身形只来自用户自选或填写的骨架类型与身高，不从照片推断体型或体重。
  • 搜索词由规则模板生成，保证可复制、无品牌偏向。
状态与边界
  • 用户未提供身形：按面部风格推荐，并标注“加入身形后更准”。
  • 着装要求为制服：只给配饰、发型与妆容方向。
  • 预算低：优先给“改变搭配而非购买”的公式。
依赖

F7 色彩、F8 风格、F3 身形；新增单品库与 prompt 段落；clothing_top 蒙版（已有）。

验收标准
  • 单品与用户色彩、风格规则冲突率为 0（规则层校验）。
  • 形象顾问盲评“可以照着买” ≥ 70%；交换测试（M11）中用户能认出“这不是我的” ≥ 70%。
成功指标
  • 复制搜索词或保存清单 ≥ 25%；标记“想要”的单品中位数 ≥ 3。

穿搭检测

›拍一张今天的穿搭，得到颜色、风格一致度与比例上的具体调整建议。 C · 3
用户问题

诊断是一次性的，穿什么是每天的问题。用户出门前需要一个懂她的“第二意见”。

预期结果

用户 15 秒内得到 1 个最值得的调整（例如“把黑色围巾换成你色卡里的雾蓝，脸会更亮”）和 2 个可选调整，并能保存为“今日穿搭”。

体验与交互
  1. 上传一张全身照（相册或系统相机拍后选择）；示例图提示“头到脚都在画面里”。
  2. 结果：服装区域分割后的色块条（实际颜色 vs 你的色卡）、风格一致度（与你的风格方向的距离，用“很贴合 / 部分贴合 / 换个方向”三档文字，不打分）、比例线（腰线、上下身分割位置）。
  3. 一个“最值得的调整”，最多两个“也可以试试”，每个都说明理由。
  4. 场合选择（通勤 / 约会 / 正式）会改变建议。
  5. “今日穿搭”记录形成日历，可回看（需轻账户）。
功能需求
  • 独立 schema outfit_check.schema.json 与独立 prompt；一次检测是一次独立请求（满足“一个生产模型”）。
  • CV：人体分割取服装区域；可分析衣物颜色、廓形、上下身分割与画面构成；不计算、不输出任何体型或体重相关量。

用户问题

“方圆框、中等粗细”在店里难以执行；男性理容建议常被敷衍。

预期结果

用户能拿着“镜框总宽 136–142 mm、鼻梁 18–20 mm、镜腿 145 mm”这样的参数去挑镜框，并看到 2–3 种形状戴在自己脸上的样子。

体验与交互

  2. 形状试戴：2–3 种形状的 AI 试看，与发型选择联动（例如突破发型配细金属框）。

状态与边界
  • 虹膜被眼镜反光遮挡：不给 mm，只给“与颧骨同宽”。
  • 用户不接受换眼镜：模块折叠为“如果哪天想换”。
依赖

anchors.py；masks.py 的 glasses 蒙版；preview。

验收标准
  • 10 位戴镜测试者，估算总宽与其舒适镜框实际总宽误差 ≤ 5 mm 的比例 ≥ 70%。
成功指标
  • 眼镜卡保存率 ≥ 15%（戴镜用户中）。

个人改进计划

›把零散建议组织成“先做什么、花多少、怎么验证”的计划。 B · 2
用户问题

V1 的 Top 5 是五条并列建议，混合了不同类别和决策重量，用户不知道先后与组合关系。

预期结果

用户得到三段计划：本周可做（免费或低成本）、下次理发时、值得投入的一次性改变；每项可勾选完成。

体验与交互
  1. 分三栏：“今天就能做”（拍照角度、发泥用法）、“下次理发”（选定方向与发型师卡）、“值得投资”（眼镜、核心上衣颜色）。
  2. 每项显示：预计花费区间、所需时间、多久能看到效果、与哪一项搭配效果更好。
  3. “怎么判断改对了”：每项给一个可观察的检验，例如“侧面照中头顶高度不再高于眉到下巴距离的 1/3”。

功能需求
  • 计划由规则层从排序后的建议生成：按 effort 和新字段 cost_band、time_to_effect 分组；pairs_with 由模型给出、规则层校验引用存在。
  • 勾选状态存于本地，有账户时同步。
状态与边界
  • 某栏为空：不显示空栏。
  • 所有建议都需确认约束：计划顶部提示“这些需要你先确认是否可接受”。
依赖

rules.py 排序；recommendations 新增字段。

验收标准
  • 任何计划项都可追溯到一条建议和至少一条观察。
成功指标
  • 至少勾选一项的比例 ≥ 30%；7 日内回来查看计划 ≥ 15%。

反馈、偏好与即时重排

›基础反馈进入第一个版本：用户说“不像我”“不喜欢”“预算变了”，推荐立即调整，无需重跑视觉模型。 A 基础 · 1　C 高级 · 3
用户问题

  2. 调整历史与撤销到上一版本。
  3. 收藏到“我的选择”，有轻账户后跨设备同步。

软保护回贴（解决长发与刘海被截断）

V1 的受保护区域是“眉线以下的整张脸”，这对短发很安全，但齐肩发、侧刘海、八字刘海需要头发盖住脸颊或额角，会被回贴硬生生截断。V2 把保护分两级：核心区（眼、鼻、口及其外扩 6 px）永远使用原图像素；边缘区（脸颊外缘、额角、下颌外缘）允许结果中被识别为头发的像素覆盖，其余仍用原图。随后做身份检查。

回贴方法比较与选择：① 现有蒙版 + 羽化（基线，最可控）；② 在边界带做 Lab 均值 / 方差颜色迁移，消除结果与原图的肤色、光照差；③ 泊松 / cv2.seamlessClone，边界最平滑，但会把结果色调渗进原图、涂抹发丝细节，也更慢。默认采用 ① + ② + 软保护；③ 作为配置开关 composite_mode: feather | seamless（qc.yaml）保留，只在 I1 小样本中明显更好时才打开。需修订 D17（见 G1）。

确定性可视化：披布与妆容

色彩和妆容的可视化不需要生成模型。披布是在下颌以下叠加一块由关键点生成形状的纯色区域；唇色是唇外轮廓减内轮廓的区域内、Lab 空间里按浓度着色并保留纹理；腮红是羽化的径向渐变；牙齿与眼睛永远在排除蒙版内。原图始终保留，可一键对照。它们在浏览器实时运行、零成本、可复现，不改变五官形状。决定（定稿）：确定性着色允许进入妆容区域，生成式编辑仍不得改动五官（修订 D4 / D17）。

身份检查与质量门

每张试看在展示前计算前后人脸特征相似度和发型区域变化量：相似度低于阈值或发型几乎没变，都视为失败并自动重生一次。注意许可：InsightFace 预训练模型仅限非商用，商用需选择许可清晰的模型或获得授权，在 I1 时定案；之前沿用“核心区逐像素不变 + 发型区域变化量”作为门槛。阈值放入 config/qc.yaml。
